# Gordon vNext — Phase 1.5: trust, semantics and exception reduction (2026-09-20/21)

Shadow mode, unchanged: nothing here is wired into Telegram or a cart,
no schedule changed, no `preferred_products` / `product_rejections` /
`adhoc_requests` / `app_state` row was written, no existing mapping was
cleaned in place. Branch `claude/gordon-work-mvp-cartpause`, commits
`4dc6902`..`8601b7b` on top of Phase 1's `851367d`.

## 1. Implementation summary

Phase 1 proved the shape; its sample also showed why it could not be
trusted: 41 "decisions", and a product layer that mapped "יוגורט Pro וניל"
to a shower gel because the old resolver's memory said so and nothing
checked meaning. Phase 1.5 puts meaning first and evidence second:

- **`vnext_semantics`** parses the household's words into a head noun,
  brand, flavor, colour, size/weight, form and *negatives* ("לא באריזת
  ואקום" → must not be vacuum; "ללא תוספת סוכר" → must be declared
  sugar-free), and classifies any shelf product from its name with an
  independent Hebrew category lexicon — never Tiv Taam's `department`,
  which is `שונות` for every row. `violations()` names every way a
  product fails a request; a category mismatch, a processed form for a
  fresh request, a contradicted qualifier or an undeclared free-of
  attribute is hard (rejected); a colour mix collapsing to one colour is
  soft (substitute at best).
- **`vnext_resolver`** gathers candidates from human confirmations, the
  old `preferred_products` rows (human = HUMAN_DECLARED; the rest =
  INFERENCE), purchase history and each chain's catalogue (head noun,
  then head + each qualifier word), runs the semantic check on all of
  them, and only then ranks survivors by evidence. Output:
  `exact_match / acceptable_match / unresolved / rejected_by_constraints`
  with confidence, why, qualifiers checked/unverified, provenance and
  every candidate's verdict. A human confirmation short-circuits to
  exact — but one that violates the request is *flagged*, not applied.
- **`vnext_reconcile`** compares every pending request with order lines
  dated after it, using the same semantic check: `likely_fulfilled`
  (a later line satisfies every qualifier), `uncertain` (head matches,
  a qualifier unverified — or a later Shufersal order whose lines are
  not synced), `active`. The request row is untouched.
- **`vnext_economics`** decides stock-up from real numbers: the deal
  price against the item's own recorded reference (`price_history` for
  Shufersal, `store_prices` for Tiv Taam), inflated-reference and
  routine-promo detection, units the household will use before spoilage
  from cadence × usual quantity under a 7-day (perishable) or 60-day
  (shelf-stable) horizon, net of a recent purchase, absolute saving.
- **`need_engine` / `shopping_plan`**: need, quantity, product and
  retailer confidence are four fields. Cadence is stratified
  (`measured` ≥3 real gaps → may reach HIGH; `weak` → ≤0.70;
  `household_fallback` → ≤0.44) and depletion alone can never
  auto-include on a thin cadence. Every item carries an
  `exception_class`: `true_user_decision` (requested product unmatched
  and substitutes differ, a stated brand not found, a stock-up above
  4 units/₪60, a chain split), `agent_resolvable` (inferred but clean —
  Gordon picks, the household can correct), `quiet`. `cart_state =
  unknown` is one plan caveat; the per-item "may already be in a cart"
  question is gone.
- **`vnext_confirmations`** — the human-confirmation API (four kinds:
  explicit statement, accepted substitution, kept exception choice,
  later correction) over a new additive table
  `vnext_product_confirmations`. Not called by anything in production;
  the resolver reads it. Repeated purchases raise *inferred* confidence
  and never write here.
- **`vnext-evaluate`** CLI (text + `--json`): the §12 metrics, the
  reconciliation, price-source freshness and a Telegram mock.

Every threshold above is a `VNextConfig` field with a
`GORDON_VNEXT_*` override.

## 8. Remaining blockers to Phase 2

1. **Still 0 human-confirmed products.** 52 of 53 plan items are
   "agent_resolvable": semantically clean, but every one is inference.
   The mechanism to accumulate confirmations exists and is unwired;
   Phase 2's first job is to feed it from real interactions (the
   exception reply, "זה הנכון", an accepted substitution).
2. **Cadence coverage**: measured for 70/390 Tiv Taam products, 0 for
   Shufersal (no line-level sync; `last_purchase` stale since 09-01).
   The strata ceilings keep the 320 others out of auto-include, which
   is honest but means "never run out" rests on 70 items today.
3. **Semantic lexicon is rules, not coverage.** ~400 Hebrew keywords;
   an unknown word is UNKNOWN and never matches a category. Real risk
   is a false *rejection* of a good product with an unusual name, not a
   false acceptance; the evaluate counter (442 rejections) should be
   sampled by a person before Phase 2 trusts it.
4. **Cart state unknown.** Not solved and not pretended: Phase 2 must
   read the cart (and the audit says those reads are unreliable) before
   anything is added; the plan carries the caveat once.
5. **Consumption-rule split** (orchestrator `added` vs watch_list
   `verified`) is untouched — reconciliation works around it by
   reading orders, it does not fix it.
6. **Reconciliation is Tiv-Taam-only in practice**; a later Shufersal
   order makes a request "uncertain", never "fulfilled", until Shufersal
   line items are synced.
7. **Price history is shallow**: 22 days for Shufersal, 14 of the last
   30 for Tiv Taam. "Routine promo" and "inflated reference" are
   measured over that window only.
8. **Runtime**: a full shadow plan takes ~2 minutes (catalogue LIKE
   searches over ~300k `store_prices` rows for ~55 terms). Fine for a
   CLI, not for a Telegram turn; Phase 2 needs an index or a cached
   shortlist.
9. **Waste, meals, events, external spend: 0 rows.** Rules tested,
   inactive on real data.

Phase 2 (wiring, execution, proactive messages) is not started.
